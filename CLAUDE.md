# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — Next.js dev server (Turbopack) on http://localhost:3000
- `npm run build` — production build; also runs type checking. Needs `DATABASE_URL` and a migrated, seeded database: `generateStaticParams` for product and collection pages queries it and must return at least one slug.
- `npm run lint` — ESLint (flat config in `eslint.config.mjs`)
- `npx tsc --noEmit` — typecheck on its own. If `LayoutProps` is reported missing, run `npx next typegen` first; it's a global generated by Next.
- `npm test` — Vitest (`vitest run`, config in `vitest.config.mts`). Unit tests sit next to the code as `src/**/*.test.ts` and cover pure logic only (cart totals, order numbers, address validation, error detection). Anything importing the DB or `server-only` is verified by running the app. One file: `npx vitest run src/lib/cart.test.ts`.
- Database (Drizzle + Neon Postgres):
  - `npm run db:generate` — create SQL migrations from schema changes in `src/lib/db/schema`
  - `npm run db:migrate` — apply migrations
  - `npm run db:push` — push schema directly (no migration files)
  - `npm run db:studio` — Drizzle Studio
  - `npm run db:seed` — load the sample catalog and collections from `scripts/seed-data.ts` (`scripts/seed.ts`, run with `tsx`). Idempotent: upserts by key and replaces each product's images. Stock rows for seeded sizes are upserted (cart lines reference them), but **a re-run resets stock quantities, names and prices to the sample values and deletes any size of a seeded product that isn't in the seed data, which cascades to those cart lines**. Use it on dev data only, never after admin edits you want to keep.
  - `npm run db:cleanup-carts` — delete guest carts untouched for 30 days (`scripts/cleanup-carts.ts`).
  - `npm run orders:expire-stale` — reconcile pending orders whose stock hold ended >10 min ago with Stripe (missed-webhook safety net; `scripts/expire-stale-checkouts.ts`, run with the `react-server` condition so `server-only` modules load).
  - Use `db:generate` + `db:migrate` rather than `db:push`; migrations are committed in `drizzle/`.
- `npm run auth:generate` — regenerates Better Auth's tables (`user`, `session`, `account`, `verification`) into `src/lib/db/schema/auth.ts`. Run this after changing the Better Auth config (new plugins or fields), then `db:generate` + `db:migrate`.
- `npm run auth:set-role -- <email> <customer|admin>` — the only way to grant or remove the admin role (`scripts/set-role.ts`).

## Environment

Copy `.env.example` to `.env` (git-ignored; `.env.local` also works and takes precedence). Required: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL`, `STRIPE_SECRET_KEY` (a restricted `rk_` key from a Stripe sandbox), `STRIPE_WEBHOOK_SECRET` (`whsec_`, printed by `stripe listen` locally). Stripe redirects back to `NEXT_PUBLIC_APP_URL`, which is inlined at build time: build with it pointing at the port you'll serve.

Env loading is split between two paths:
- Next.js loads `.env` (and `.env.local`) automatically for app code.
- `drizzle.config.ts` and `scripts/seed.ts` load `.env.local` then `.env` explicitly via `dotenv` (same precedence as Next), because they run outside Next.

## Architecture

The app is the App Router with `src/` and the `@/*` alias. The pieces that span multiple files:

- **DB client** — `src/lib/db/index.ts` creates a Drizzle instance over Neon's HTTP driver (`drizzle-orm/neon-http`) and throws at import time if `DATABASE_URL` is missing. Anything that imports `@/lib/db` therefore needs the env var, including build-time route collection.
- **Schema** — all tables live in `src/lib/db/schema/`, and `schema/index.ts` is the barrel that Drizzle and the DB client read. New table modules must be re-exported from there to be picked up. Drizzle config points at this directory.
- **Auth** — `src/lib/auth.ts` is the server-side Better Auth instance (Drizzle adapter on the `schema` barrel, email + password enabled, `nextCookies()` plugin last so Server Actions can set the session cookie). The HTTP handler is `src/app/api/auth/[...all]/route.ts`; the browser client is `src/lib/auth-client.ts` (unused so far: the forms call Server Actions). Email verification and password reset are off until there is a mail provider.
  - `src/lib/auth-session.ts` (`server-only`): `getSession()`, `requireUser(returnTo?)` and `requireAdmin(returnTo?)`. `getSession` calls `connection()` first so the session query never runs during a prerender or runtime prefetch (Next aborts the fetch and Better Auth logs an INTERNAL_SERVER_ERROR). Use `requireUser()` in every account page, query and action, and `requireAdmin()` in every admin page, query and action; `src/proxy.ts` only does an optimistic cookie-presence redirect for `/account/*` and `/admin/*`.
  - Roles: `user.role` (`customer` | `admin`, default `customer`) is a Better Auth `additionalFields` entry with `input: false`, so sign-up and `update-user` can't set it. `src/lib/roles.ts` holds `ROLES` / `isAdmin`. `requireAdmin()` sends signed-out visitors to sign-in and gives signed-in non-admins `notFound()` (not `forbidden()`, which needs the experimental `authInterrupts` flag). There is no `cookieCache`, so a role change applies on the next request. The admin area is described under Storefront → Admin; the `admin()` plugin (bans, impersonation, user management) is deliberately not used.
  - Sessions: Better Auth defaults written out in `auth.ts` (7 days, extended daily while in use). Trusted origin is `BETTER_AUTH_URL`: requests to `/api/auth/*` from another origin (e.g. a `next start -p 3001` checked from port 3001) get `403 INVALID_ORIGIN`. Server Actions call `auth.api` directly and aren't affected.
  - `src/lib/paths.ts` holds `safeNextPath` (same-site redirect targets only), kept pure so it can be unit-tested.
- **Server Actions vs. server modules** — everything exported from a `"use server"` file is a public endpoint. `src/lib/actions/*` are the thin, validated entry points (zod). Anything that takes a trusted argument such as a user id (`mergeGuestCart(userId)`) lives in `src/lib/db/mutations/*`, which is `server-only` but not `"use server"`.
- **Next.js config** — `next.config.ts` enables `cacheComponents` and `partialPrefetching`, and adds a Tailwind Turbopack loader for `*.css`. These affect how pages and data fetching are written, so check the Next docs before changing them.

## Storefront

- **Design system** — everything lives in `src/app/globals.css` (Tailwind v4, no `tailwind.config`). Use the semantic tokens (`bg-background`, `text-muted-foreground`, `border-border`, `bg-primary`, `text-danger/success/warning`) and primitives (`shell`, `shell-content`, `shell-narrow`, `section`, `btn btn-primary|secondary|ghost` with `-sm|-lg|-icon|-block`, `link`, `link-reveal`, `link-muted`, `input`, `eyebrow`, `heading-1/2/3`, `text-display`, `product-grid`, `media-frame`, `hero`, `surface-inverse`, `surface-muted`) instead of raw colors or ad-hoc spacing. Buttons are pills, images are square-cornered, borders are 1px hairlines. There is no OS-driven dark mode; `dark:` only applies inside `.dark` / `.surface-inverse` / `.hero`.
- **Layout** — `src/app/layout.tsx` wraps every page in `SiteHeader`, `<main id="main">` and `SiteFooter`. Shared components are in `src/components/`; `page.tsx` (homepage) composes its sections locally.
- **Catalog** — products, categories and stock are in Postgres (`src/lib/db/schema/catalog.ts`: `categories`, `products`, `product_images`, `product_stock`). Prices are integer cents (`priceCents`; `formatPrice` takes cents). Stock is a quantity per size in `product_stock`, which is not a variant table.
  - `src/lib/db/queries/catalog.ts` (`server-only`) holds the reads (`getProduct`, `getProductSlugs`, `getNewArrivals`, `getRelatedProducts`; collections have their own cached reads in `queries/collections.ts`). Each uses `"use cache"` + `cacheLife("hours")` + `cacheTag("products")`, so pages prerender. After writes that change stock or products, call `updateTag("products")` (Server Action) or `revalidateTag`. They map rows to the storefront `Product` type.
  - `src/lib/catalog.ts` holds only types and pure helpers (`getStockState`, `getTotalStock`, `isOneSize`, `formatPrice`, hrefs). Client components import it, so it must never import the DB.
  - `src/lib/content.ts` holds homepage editorial content (hero, category tiles, features, boutique). The hand-picked Essentials list now lives in the `essentials` collection. New Arrivals are the newest products by `created_at`.
  - In relational queries (`db.query.*`), Drizzle rewrites table-qualified columns in `where`/`orderBy` SQL to the root alias, which breaks subqueries on other tables. Use unqualified column names inside such subqueries.
- **Product page** — `src/app/products/[slug]/page.tsx`, prerendered via `generateStaticParams`. `ProductPurchase` (client) calls the `addToCart` Server Action.
- **Collections** — `/collections/[slug]` (`src/lib/db/queries/collections.ts`) resolves a slug as the virtual `new-arrivals`, then a category, then a curated collection (`collections` + `collection_products`, seeded: `essentials`, `autumn-winter`, `knitwear`). The homepage Essentials rail reads the `essentials` collection. Sort (`?sort=`) and `?inStock=1` are plain links; the cached query takes them as arguments. `bags` has no products yet and shows the empty state. Slugs not listed by `generateStaticParams` render on demand.
- **Cart** — `carts` / `cart_items` (`schema/shop.ts`). Guests are identified by the httpOnly `cart` cookie (cart id, 30 days); a signed-in user has one cart keyed by `user_id`. A cart line stores no price. `cart_items` has a composite FK to `product_stock (product_id, size)`, so a line can only point at a real size and is removed if that size is. Reads (`queries/cart.ts`: `findCartId`, `getCart`, `getCartCount`) are request-scoped (`react` `cache`), uncached, and must be inside `<Suspense>`. Writes are in `db/mutations/cart.ts`, called from `actions/cart.ts`. At sign-in/sign-up `mergeGuestCart` moves the guest cart into the user's (single SQL statement). Quantity rules (`MAX_LINE_QUANTITY`, `purchasableQuantity` = min(saved, stock, max)) live in client-safe `src/lib/cart.ts`; the header badge shows saved quantities.
- **Checkout and orders** — `startCheckout` (`actions/checkout.ts`) first ends any checkout still open for the same bag (`endOpenCheckoutsForCart`), re-prices from the DB and rejects the submit if the total the shopper saw no longer matches (`expectedTotalCents`). It then runs one `db.batch`: insert order (`pending`, `cart_id`, `reserved_until`), insert order items (snapshots of name/price/image), decrement `product_stock`. The bag is **not** cleared there. `product_stock` has `CHECK (quantity >= 0)`, so an oversold line aborts the whole batch atomically; `isOutOfStockError` (`db/errors.ts`) recognises it. neon-http has no interactive transactions, so keep new multi-step writes in a batch or one statement. It then creates a Stripe-hosted Checkout Session (inline `price_data` from the order rows, `client_reference_id` = order number, `expires_at` = `reserved_until` ≈ 31 min, idempotency key per order), stores its id, sets a `last_order` cookie (how a guest may reopen `/checkout/confirmation/[orderNumber]`) and redirects to Stripe. Order numbers are random (`LE-` + 10 chars), so they are safe in URLs; reads in `queries/orders.ts` are always scoped to a user or that cookie.
  - **Payments (Stripe)** — `src/lib/stripe.ts` (`server-only`, API `2026-08-26.dahlia`, throws at import without `STRIPE_SECRET_KEY`, so the build needs it too). Pure rules and Stripe params are in `src/lib/payments.ts` (unit-tested). An order only changes state through `reconcileCheckoutSession` (`src/lib/checkout-reconcile.ts`), which re-reads the session from Stripe and checks `amount_total`/currency against the order: `paid` → `markOrderPaid`, which also removes the bought lines from the bag; `expired` or a failed delayed payment → `cancelOrder`, which returns the stock; complete but unpaid → still `pending`, held with `reserved_until = null`. Callers are the webhook (`/api/stripe/webhook`: signature check, `stripe_events` dedupe by event id), the success page (`?session_id=`), the `cancel_url` route (`/checkout/cancel`, which expires the session and returns stock now), and `npm run orders:expire-stale` (missed webhooks). The state changes in `db/mutations/orders.ts` are single SQL statements guarded by `status = 'pending'`, so replays and races are no-ops. Nothing from the browser decides an amount or a status.
  - After a stock change, the first request to a product page can still serve the old prerendered shell (it revalidates in the background); the next request is fresh. `addToCart` and `startCheckout` always check live stock.
  - Shipping methods and prices are constants in `src/lib/cart.ts`.
- **Account** — `/account/sign-in`, `/account/sign-up` (outside the route group), and `src/app/account/(portal)/` with the shared tab layout: overview (recent orders, name, password), `orders`, `orders/[orderNumber]`, `addresses` (add, edit via `?edit=<id>`, default, delete). Address-book actions are in `actions/account.ts` and scope every query to `requireUser()`. Saved addresses are copied into orders, never referenced. One default address per user is enforced by a partial unique index; changing it is a two-statement batch. A password change rotates the session cookie, which re-renders the page and drops local form state, so its confirmation travels in the URL (`?updated=password`).
- **Admin** — `/admin` (overview) and `/admin/products` (list; editor via `?edit=<id>`, so no `generateStaticParams`), with the shared `TabNav` in `admin/layout.tsx`. Reads are `queries/admin-catalog.ts` (uncached, so stock is live; includes units held by pending orders), writes are `db/mutations/catalog.ts`, actions are `actions/admin.ts`, validation is the pure, unit-tested `src/lib/product-form.ts`. Every admin page, query and action calls `requireAdmin()`. After a write the action calls `updateTag(CATALOG_TAG)` (one tag covers product pages, collections and rails) and `refresh()`.
  - Stock is edited as relative changes (`quantity = quantity + delta`), never set outright: `quantity` is units still sellable with checkout holds already taken out, so an absolute write would erase sales or cancellations that land while the admin edits. Below zero hits the `CHECK` and the whole batch is refused (`isOutOfStockError`). Sizes can be added (appended to the run) but not renamed or deleted, because cart lines cascade from stock rows and pending orders restock by `(product_id, size)`; retire a size by bringing it to 0. Products can't be deleted and slugs can't change (order history links to them). Saving details replaces the product's images; at least one is required and hosts are limited to `IMAGE_HOSTS` (keep in sync with `next.config.ts`).
- **Forms** — Server Action forms use `useActionState` with a `{ error, fieldErrors, values }` state; echo submitted `values` back as `defaultValue` because React resets the form after the action. `FormField` and `AddressFields` are the shared inputs.
- **Not real yet** — wishlist, newsletter and "Notify me" only change local UI state and persist nothing; tax, refunds, order emails, email verification and password reset do not exist. Links that still 404: `/search`, `/wishlist`, `/help/*`, `/legal/*`, `/about*`, `/stores`, `/contact`.

## Next.js 16 gotchas hit so far

- With `cacheComponents` + `partialPrefetching`, reading `params` outside `<Suspense>` is a validation error: render a `<Suspense>` in the page and `await params` in a child. Dynamic routes also need `generateStaticParams` returning at least one param. `dynamicParams` is unavailable.
- Avoid `Date.now()` / `Math.random()` in server components; they block prerendering.
- `Image` `priority` is deprecated; use `loading="eager"` + `fetchPriority="high"` for above-the-fold images. Remote hosts must be allowed in `next.config.ts` (`images.unsplash.com` is).
- Unknown slugs hit `notFound()`. Because `params` is read inside Suspense, an unlisted slug streams with status 200 plus `noindex` and the 404 UI, in dev and in the production build alike.
- Client components that call `usePathname()` / `useSearchParams()` (e.g. `TabNav`) need a `<Suspense>` boundary on dynamic routes or the build fails.
- Anything that queries the DB per request (session, cart) must run behind `connection()`, `cookies()` or `headers()`, inside Suspense. Otherwise it can start during a prerender and Next aborts the fetch.
- With cached components, `updateTag` (Server Actions only) is the read-your-own-writes call; `revalidateTag` is for route handlers and background invalidation.
- `useActionState` forms: the form is reset after the action, so a password field is cleared on error. A test that types before the result arrives will race it.

## Workflow notes

- Claude's access to `.env*` files is denied in `.claude/settings.json`; ask for values rather than reading them. `.env.example` was deliberately not pushed to GitHub yet.
- Browser checks: there is no e2e suite in the repo. For ad-hoc runs, build, `next start -p 3001`, and drive Edge with `playwright-core` installed *outside* the project (`executablePath` pointing at `msedge.exe`), so no browser download or project dependency is needed. Match form fields with `getByLabel(text, { exact: true })` plus `locator("visible=true")`: the footer newsletter is also labelled "Email address", and Next keeps the previous route hidden in the DOM during client navigation.
- Formatting follows Prettier at `--print-width 120` (there is no config file; run `npx prettier --print-width 120 --check <files>`).
- The user may already have `npm run dev` running on port 3000; a second `next dev` in the same project refuses to start. Use `next start -p <port>` after a build, or reuse the running server.
- Local branch is `master`, tracking `origin/main` (https://github.com/NicholasCloud4/LeClothing.git).
